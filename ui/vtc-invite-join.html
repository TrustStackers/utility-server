🤝 Invite & Join a VTC

Scenario 5. Discovery is deliberately OOBI-only — no public directory, no DHT search. An admin mints a shareable invitation string for their community; a prospective member decodes it and submits a join request that lands as a pending row in memberships. Talks to POST /vtcs/:id/invite, POST /vtcs/:id/join, and POST /memberships/:id/approve.

← Back to dashboard · Manage a VTC →

Cross-node consideration: the invite string encodes the community's real DID plus this utility-server's own libp2p peerId/multiaddrs — decodable by any node type (including the agent/TUI node) using the shared OOBI codec. What is not yet wired up: a remote node that decodes an invite still has no cross-node message to carry a join request into this node's memberships table — today a join request only lands here if the applicant's identity already exists as a local identities row on this node. Likewise, an approval decision made here isn't pushed back out over TSP to the requester's own node. Two nodes' local views of the same membership can silently diverge until a real RFI/RFA-style membership message type exists. See utility-server/src/routes/layer5-applications/vtc-invite.ts.
